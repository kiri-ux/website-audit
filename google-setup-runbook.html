Wiring up Google access, end to end

Three environment variables, two Render services, four Google APIs, and one ordering trap that costs an afternoon if you hit it. Work down the list — every step says where it happens and how to tell it worked.

build 2026.08.20-33 ~30 minutes progress saves in this browser

The end state: the audit form's Check Google access button returns three green pills — Search Console, GA4, Tag Manager — and audits fill the 38 Search Console and Analytics rows instead of reporting them as unmeasured.

Phase 0

Get the code live first

This one is genuinely first, not housekeeping. A refresh token freezes the scopes it was granted at the moment of consent — so a token minted against the old code carries Search Console and Analytics only, and no amount of configuration adds Tag Manager to it later.

01
Browser

Get build 2026.08.20-33 live

Already done — check and move on

Open https://vici-audit-api.onrender.com/healthz. If "build" reads "2026.08.20-33", this step is finished. Tick it and go to step 02.

The rest of this card is here for the next build. Nothing below needs a terminal — it is the same upload you have been doing.

What the zip is. A partial copy of the project: only the files that changed, each already sitting at the path it belongs at. Expanding it gives you folders named app, engine, seed, tests — the same names GitHub already has. Uploading them replaces those files and leaves the rest of the repo alone.

  1. Expand it. Double-click the zip in Downloads. Note that the browser strips the hyphens from the name — viciaudit2026.08.2033.zip is the right file.
  2. Open the repo at github.com/kiri-ux/website-audit.
  3. Add file → Upload files, then drag in the expanded folders and any loose files beside them. GitHub matches each one to its existing path.
  4. Commit changes. That commit is what Render is watching.
  5. Wait for both services. vici-audit-api and vici-audit-worker rebuild independently — two to four minutes each. Both must read Live. The worker is the one that runs the audits and the easy one to forget.
Why check the build number at all

Running against code that did not actually land produces a report that looks completely normal and is quietly wrong. The number in /healthz is the only way to tell from the outside, which is why every build gets a new one.

Phase 1

Google Cloud Console

Reuse the project Site Scanner already uses. The Tag Manager API is enabled there and the consent screen is configured — reusing it skips a whole failure state. Google reorganized this area into Google Auth Platform, with four sections: Branding, Audience, Data Access, Clients.

02
Google Cloud

Find the project Site Scanner authenticates against

On the Site Scanner service in Render, open the GTM_OAUTH_CLIENT environment variable. It holds a whole OAuth client JSON. Two fields matter:

project_id
The Google Cloud project to reuse. Switch to it with the project picker at the top of the console.
installed or web
The top-level key. This is the client type, and it decides step 03.
Expect "installed"

Site Scanner mints tokens with InstalledAppFlow.run_local_server(), which is a Desktop client. Desktop clients authenticate over a loopback address and have no redirect URI registered for a server. Ours needs one.

03
Google Cloud

Create a Web application client in that same project

Skip this only if step 02 showed "web" and our callback is already among its redirect URIs.

  1. Go to console.cloud.google.com/auth/clients — the Clients section of Google Auth Platform.
  2. Create client → Application type: Web application.
  3. Name it something you'll recognize next year — vici-audit-web.
  4. Under Authorized redirect URIs, add exactly:
https://vici-audit-api.onrender.com/oauth/google/callback

Then copy the Client ID and Client secret off the panel that appears. You'll paste both in step 07.

This string must match character for character

https, not http. No trailing slash. Render terminates TLS in front of the app, so the app itself sees http:// — our code rewrites it back to https:// before handing it to Google precisely because Google would otherwise reject the mismatch. If your API is on a custom domain, register that host instead.

Why the same project

API enablement, the consent screen, and its verification status all live at the project level, not the client level. A new client in the same project inherits all of it. A new project inherits none of it.

04
Google Cloud

Enable all four APIs

Site Scanner only ever needed one of these. Under APIs & Services → Library, search for each and confirm it's enabled:

Google Search Console API
Impressions, clicks, index coverage, sitemap status — most of the 22 GSC rows
Google Analytics Data API
Sessions, conversions, engagement — the GA4 reporting rows
Google Analytics Admin API
Property configuration, enhanced measurement settings
Tag Manager API
Container and tag reads. Already on if you reused the project.
A disabled API and a missing scope both return 403

They are different problems with different fixes, and until this build they produced the same message — "re-authorize each login" — which on a disabled API is half an hour that changes nothing. Build ‑33 tells them apart: an unenabled API now says "the Tag Manager API is not enabled on the Google Cloud project this OAuth client belongs to."

05
Google Cloud

Check the publishing status before you mint anything

Open console.cloud.google.com/auth/audience and read the publishing status.

Testing mode expires your refresh tokens in seven days

Google is explicit about it: an authorization by a test user expires seven days from consent, and if the client requested offline access, the refresh token expires with it. Everything would work perfectly for a week and then every Google row would go blank at once — which is a miserable thing to debug, because nothing changed.

You need In production, or Internal if the project sits in a Workspace org and every login is in it. Internal is the cleaner answer for six agency logins and needs no verification review.

Verify

The Audience page reads In production or the app type reads Internal. If Site Scanner has run for months on these credentials, this is almost certainly already fine — confirm rather than assume.

Phase 2

Render environment variables

All three values go on both services. Not redundancy — they do different jobs. The worker calls Google during a run; the API runs the access check on the audit form, in its own container with its own environment.

06
Both services

Understand what you're setting, before you set it

GOOGLE_CLIENT_ID
Your OAuth app's public identifier, from step 03
GOOGLE_CLIENT_SECRET
That app's password, from step 03
GOOGLE_TOKENS
JSON {"label": "refresh_token"}, one entry per Vici login. Minted in step 09.

A refresh token is not a credential on its own. It's a coupon that only the client ID and secret pair can redeem: our code posts all three to Google and gets back a short-lived access token. Miss any one and that exchange returns nothing — which is why setting GOOGLE_TOKENS by itself did nothing at all.

07
Both services

Set the client pair on vici-audit-api and vici-audit-worker

Identical values on both. Let both redeploy.

GOOGLE_CLIENT_ID      = <from step 03>
GOOGLE_CLIENT_SECRET  = <from step 03>
Verify

Open https://vici-audit-api.onrender.com/healthz and the worker's equivalent. Both should now report "client_id": true, "client_secret": true inside the "google" block. Tokens will still be false — that's step 09.

08
API only

Invent a password and set it as OAUTH_SETUP_TOKEN

This value is yours to make up. It is not issued by Google and it is not looked up anywhere — it is a password that unlocks the two minting routes, which return 404 without it. They stay off unless you are actively using them, and you turn them back off in step 11.

On vici-audit-api → Environment, add a variable with any long random string as its value:

OAUTH_SETUP_TOKEN
e.g. akxrntlyt0q050y77k7wff08hxx4 — or anything else long and random. Keep it where you can copy it; step 09 needs the exact string.
Verify

https://vici-audit-api.onrender.com/healthz reports "oauth_setup": true. If it reads false, the variable did not save or the redeploy has not finished — and step 09 will return {"detail":"not found"} until it does.

Phase 3

Mint the tokens

Once per Vici login that holds client properties. Google caps how many properties one login can hold, which is why this is a JSON object of several rather than a single token.

09
Browser

Walk each login through the consent screen

In a browser signed in as that Google login — not as you, unless it's yours — open a URL built from two things you already have:

t=
The exact string you invented in step 08. Not the words OAUTH_SETUP_TOKEN — the value.
label=
A name for this login, chosen by you. Use the labels already in GOOGLE_TOKENS so the new token replaces the old entry rather than adding a duplicate. Open that variable on Render — the labels are the left-hand keys.

So if your token were akxrntlyt0q050y77k7wff08hxx4 and the login were reporting-zone, the whole URL is:

https://vici-audit-api.onrender.com/oauth/google/start?t=akxrntlyt0q050y77k7wff08hxx4&label=reporting-zone

You should land on a Google sign-in screen. Approve it. The page that comes back prints the complete merged JSON for every login the service knows about — not just the one you added.

Repeat per login, changing label= each time, and take the newly merged value from the last one.

If you get {"detail":"not found"}

The route is 404ing, which means one of two things: OAUTH_SETUP_TOKEN is not set on the API (check /healthz for "oauth_setup": true), or the t= in your URL does not match its value exactly. A placeholder left in the URL bar looks identical to a wrong password from the server's side.

"Google did not return a refresh token"

Google issues one only on the first consent for a given client-and-login pair. If you hit this, remove the app at myaccount.google.com/permissions for that login and try again.

10
Both services

Paste the merged JSON as GOOGLE_TOKENS on both services

Replace the whole value — it already contains every login. It looks like this:

{
  "seo-main": "1//0abc...",
  "reporting-zone": "1//0def..."
}
Both, not just the worker

The success page used to say "paste this on vici-audit-worker". Following that exactly leaves the access preflight broken on the API and produces the confusing state where audits fill their Google rows but the form's check button insists nothing is configured. Fixed in ‑33; mentioned here because the habit is easy to keep.

11
API only

Unset OAUTH_SETUP_TOKEN

Both minting routes disappear with it. Leave it set and anyone who guesses the value can start an OAuth flow against your client.

Verify

https://vici-audit-api.onrender.com/oauth/google/start now returns a 404 page, and /healthz reports "oauth_setup": false.

Phase 4

Confirm it actually works

In this order. Each step rules out a whole class of cause, so a failure at step 13 means something quite specific once 12 has passed.

12
Both services

Check /healthz on each service

Open each service's health URL in a browser tab — https://vici-audit-api.onrender.com/healthz, and the worker's own URL from its page in the Render dashboard. It used to report only google_client — one of three required values, all producing the identical symptom when missing. A health check confirming the part that's fine is worse than none, so ‑33 reports the whole picture:

"google": {
  "client_id":     true,
  "client_secret": true,
  "tokens":        true,
  "logins":        2,
  "ready":         true
}

Counts only — never labels, and obviously never the tokens themselves.

Verify

"ready": true on both services before going further. logins should match the number of times you ran step 09.

What healthz deliberately won't tell you

Whether those tokens carry the Tag Manager scope. Answering that means calling Google, and a health check that touches a dependency is what once made /healthz unanswerable under load and got the instance pulled by Render. The next step answers it instead.

13
Browser

Run the access check on a real client

Open Site Scanner, enter a client URL, and press Check Google access. Three pills come back, and their colors mean different things:

PillMeansWhose move
GreenFound, and it names the property and which login saw itNobody — you're done
AmberA gap on our side: an unset variable, an unapproved scope, a disabled APIOurs. The pill says which.
RedThe grant genuinely isn't thereThe client — ask them to add the login to the property
Verify

Three green pills is the finish line. ready: true plus a red Search Console pill is also a success for this runbook — it means the configuration is right and that particular client hasn't added your login yet.

Then run one real audit with Search Console, Analytics, off-page ticked and confirm the GSC and GA4 rows carry numbers rather than "Need access".

Can Site Scanner keep running through all this?

Yes, and the tokens flow one direction. Site Scanner's tokens carry tagmanager.readonly only, so they can't answer Search Console or GA4. Ours, minted at ‑31 or later, carry all three including Tag Manager — and the JSON shape is identical.

So during the transition you can paste our GOOGLE_TOKENS value straight into Site Scanner's GTM_TOKENS and run both tools from one set. The catch: a refresh token is bound to the client that issued it, so point Site Scanner's GTM_OAUTH_CLIENT at the new Web client too, or keep its own tokens until you retire it.
